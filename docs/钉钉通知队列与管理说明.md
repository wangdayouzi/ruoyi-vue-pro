# 通用钉钉待发送通知

停后端后，先执行 `sql/postgresql/增量/2026-11-04-01-dingtalk.sql`，再执行 `sql/postgresql/增量/2026-11-04-02-reagent.sql`，更新前后端并启动后端。钉钉脚本包含基础表、队列表和控制台菜单；试剂脚本同步加急入库模板和旧队列字段。

菜单：系统管理 → 钉钉消息 → 通知管理。支持按业务编号、模板编码和状态查询，查看接收人、时间、内容参数和操作记录。查询权限为 `system:dingtalk-notification:query`，通知操作为 `system:dingtalk-notification:manage`。角色和租户套餐按需授权；菜单变更后重新登录。无需给项目组和样品组开放通知运维权限。

## 人工处理

- 待发送通知可填写原因后取消；认领与取消竞争时通过状态条件保证只有一方成功，不能撤回已认领或已发送消息。
- 仅发送失败或结果未知可以人工重发。未知结果必须勾选“已核实接收人尚未收到该消息”。保存操作人及原因，重发创建新请求，原通知和原发送记录不修改。
- 每条原始通知最多人工重发3次；只允许对最新一次结果处理。对原始记录加行锁，同一通知并发重发只生成一条新记录。不同租户不能查询、取消或重发彼此通知。
- 重发时及实际发送前均检查有效期和业务有效性，已结束、改期或过期的临期消息不能继续发送。未知结果和失败都不会自动重发。

## 统一发送任务

发送入口为原有 Quartz 任务列表中的“钉钉通知发送”，处理器 `dingTalkNotificationSendJob`，默认 Cron 为 `0/30 * * * * ?`，参数留空，任务重试次数为0。它调用 `DingTalkNotificationQueueService.dispatch` 读取到期通知，每批最多100条。没有代码内的 `@Scheduled`，也没有加急业务周期扫描任务。

首次重启时 `DingTalkNotificationJobInstaller` 通过原 `JobService.createJob` 同时登记 `infra_job` 和 Quartz 调度，使用事务锁防止多实例重复安装。不直接写 Quartz 系统表；已有任务的 Cron、暂停状态不覆盖。任务在“基础设施 → 定时任务”中可调整、暂停、执行一次和查看日志。数据库读取或认领异常抛给原任务框架记录为失败；单条消息发送结果在通知管理查看。生产环境需保持原有 Quartz 正常运行。

业务不需要各自维护发送定时任务。使用数据库行锁及 SKIP LOCKED 认领，多个实例不会同时处理同一条任务。数据库表是部署级共享队列，认领后按记录租户建立发送上下文。

通知包含模板编码、参数快照、明确接收人、业务编号、发送时间、可选失效时间及可选业务检查器。人员和部门范围在业务入队时解析；修改模板默认人员不会改动已经排队的接收人。

状态：0待发送、1处理中、2钉钉已受理、3结果未知、4明确失败、5取消、6过期。钉钉已受理不代表员工已读。处理中超过10分钟转为结果未知；未知和失败都不自动重试，防止真实发送后发生异常造成重复推送。记录不自动删除。

唯一键为租户、requestId、userId。重复登记同一内容不新增记录；同一个请求编号不允许改用另一份消息内容。仍复用钉钉发送模块自身的幂等记录，防止重复调用。业务修改应采用新版本的请求编号。

## 业务接入

注入 `DingTalkNotificationQueue`，在业务事务内提交计划，部门展开、有效账号筛选和去重均由通用通知模块完成：

```java
var plan = new DingTalkNotificationPlanReqDTO();
plan.setRequestId("business-event-123");
plan.setTemplateCode("business_notice");
plan.setBusinessId("business:123");
plan.setUserIds(List.of(10L));
plan.setDeptIds(List.of(20L));
plan.setIncludeChildDepts(true);
plan.setExcludedUserIds(List.of(30L)); // 可选：排除操作人等
plan.setParams(Map.of("name", "示例"));
plan.setSendAfter(LocalDateTime.now());
queue.enqueuePlan(plan);
```

`DingTalkNotificationRecipientApi.resolve` 是统一人员范围解析入口，模板默认接收范围、业务保存时的资格校验、通知计划入队共同复用它。包括启用部门的成员、可选的启用子部门、显式人员，过滤不存在或停用账号并去重；不因未绑定钉钉而静默剔除计划人员，未绑定问题由独立发送记录呈现。停用部门分支不向下展开。

业务如有专属资格要求，调用 `queue.enqueuePlan(plan, userId -> ...)` 提供资格判断。该判断只在入队中执行，不进入数据库、不参与未来发送。通用系统模块不引用加急入库模板编码、业务权限或实现类。原模板功能仍保留“默认接收人须已绑定钉钉”的通用校验，加急入库的样品组权限由加急业务判断。

计划最多选择1000名显式人员、100个部门，展开后超过20名也由通用队列逐人保存，不要求业务拆分。最终队列每行只有一个 `user_id` 和单人消息请求，排除人员及部门不会交给定时发送任务；某人发送失败不会阻断其他记录。部门成员变化不追改已经落库的接收人快照，生成新计划时重新读取成员。

原 `enqueue(DingTalkMessageSendReqDTO, sendAfter, expiresAt, guardType, businessVersion)` 保留兼容明确接收人的旧调用。两种入口复用同一持久化、幂等和发送逻辑。业务事务回滚，计划中所有人员的入队记录一起回滚。

需要在发送前重新确认业务有效性时，实现 `DingTalkNotificationGuard`，提供唯一 businessType、displayName 和 applicable(businessId, version)。返回 false 后任务被取消；检查器缺失/异常时记录未知，不冒险发送。`cancel(businessId)` 可取消当前租户该业务下尚未认领的任务，不会撤回已经发出的钉钉消息。

## 加急入库接入

- 新增、修改、进度等业务事件在事务提交前登记待发记录，队列与业务一起提交，回滚时一起回滚。真实发送由统一任务执行，网络发送失败不会回滚已经保存的业务；若待发队列本身不能写入，业务事务不能报告成功。
- 新增、修改、接手或进度变化时，提前把临期通知写入队列，发送时间为“截止时间减120分钟”。已进入提醒窗口时计划立即发送，已逾期不再创建临期通知。没有周期扫描业务表。模板仍为 `sample_urgent_notice`。
- 需求变更仅取消旧的待发临期通知，保留即时事件通知；重新生成当前版本及当前处理人的提醒。完成、取消时不再新建临期提醒。补充说明不重排临期提醒。
- `SampleUrgentNotificationInitializer` 在应用启动时一次性补齐历史未结束需求，逐条事务内加锁、按当前版本检查是否已有记录；不会重建已发送或取消的版本。不负责发送，也不是定时任务。缺少接收配置时记录业务提醒异常；补齐后可重新启动以补建尚无通知记录的需求。
- 临期任务的有效期为截止时间，发送前由 `SampleUrgentNotificationGuard` 检查未结束、版本一致、尚未过期以及提醒开关。已完成、已取消或变更版本的旧提醒不再发送。
- 没有操作人参与的自动提醒保留原接收规则：已接手通知处理人，未接手通知本次选择的管理员部门或人员；仅未配置范围的历史预约沿用模板默认范围。

## 验证

`DingTalkNotificationQueueTest` 在独立临时 PostgreSQL schema 中验证持久化、幂等、延时、失效、业务检查、取消、未知状态不重发、人工重发上限、并发重发、租户隔离、事务回滚，不扫描实际队列，不发送真实钉钉消息。测试结束删除临时 schema。

显式设置 `SAMPLE_URGENT_PG_TEST=true` 和 `SAMPLE_URGENT_TEST_DB_PASSWORD` 后运行对应测试；正常测试默认跳过数据库用例。

通知管理不提供业务提醒设置，统一任务仅按计划发送时间执行。加急入库的提前120分钟由业务代码固定计算；原策略表在已安装数据库中可保留，但代码不再读取或依赖它，无需删表。
