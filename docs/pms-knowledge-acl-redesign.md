# PMS 知识库权限体系设计与验收（v2）

> v1 的问题与本次修正，见文末「附录 A：相对首版的变更」。本文件是唯一有效的权限设计口径，
> 与 `sql/postgresql/pms-knowledge-acl.sql` 同步维护。

## 1. 目标

知识库（LIBRARY）、文件夹（FOLDER）、文档（DOCUMENT，含文档下的子文档）构成一棵资源树。
本设计要保证四件事：

1. **每个资源恰好一个 ACL 节点**，不再出现多个对象共用 `permission_id`；
2. **能力用操作位表达**，且覆盖真实业务动作（下载、移动、分享、彻底删除、审阅、导出、互动、打印…），
   不再用「一个等级」同时表达多种能力；
3. **允许 + 拒绝**同时存在，拒绝优先，从而能在不关闭继承的前提下收窄某个子目录；
4. **所有读写入口走同一个鉴权服务**，有效位由服务端算，绝不接受前端提交的位或旧等级。

同时明确工程要求：并发保存不丢授权、变更可审计、存量数据可迁移可回滚、批量列表不退化成 N+1。

## 2. 资源树与 ACL 节点

```
LIBRARY ─┬─ FOLDER ─┬─ FOLDER ─── DOCUMENT ─── DOCUMENT(子文档)
         │          └─ DOCUMENT
         └─ DOCUMENT
```

- 每个资源一个节点：`(object_type, object_id)` 唯一（软删除后不占用唯一性）。
- 节点记录 `library_id`、`parent_id`、`inherit_parent`，以及**物化路径** `path`（形如 `/1/9/12/`，根在前、含自身）
  和 `depth`。`path` 让「取一条祖先链」变成一次批量查询，而不是逐级递归。
- 根节点：`parent_id = null`、`inherit_parent = false`、`depth = 0`、`path = /{id}/`。
- 父节点规则：文件夹的父只能是库或文件夹；文档的父可为库、文件夹或文档；父节点必须属于同一知识库。
- 禁止环（移动/恢复时用 `parent.path.startsWith(node.path)` 判定）和孤儿节点（迁移自检负责兜底）。

## 3. 操作位（13 位）

| 位 | 动作 | 语义 |
| ---: | --- | --- |
| 1 | `VIEW` | 浏览目录、读取属性/正文、预览当前与历史版本 |
| 2 | `DOWNLOAD` | 下载当前或历史源文件 |
| 4 | `CREATE` | 在库根、文件夹或父文档下新增子项/上传 |
| 8 | `EDIT` | 修改当前对象属性/正文、上传新版本、重命名 |
| 16 | `DELETE` | 把当前对象移入回收站 |
| 32 | `MANAGE` | 查看/修改 ACL、授予他人权限 |
| 64 | `MOVE` | 移动当前对象（换父节点或换库） |
| 128 | `SHARE` | 创建、修改、关闭内部分享与外部只读链接 |
| 256 | `PURGE` | 从回收站彻底删除 |
| 512 | `REVIEW` | 提交有效性审阅结论、配置审阅规则 |
| 1024 | `EXPORT` | 导出内容包/批量导出源文件 |
| 2048 | `INTERACT` | 评论、点赞、关注等互动 |
| 4096 | `PRINT` | 在线预览允许打印（OnlyOffice 只读模式下的打印位） |

约定：

- 1~32 与首版一致，便于存量数据按位迁移；`ALL = 8191`。
- **允许位非空时必须包含 VIEW**（否则无意义）；拒绝位可以是任意子集。
- 同一能力只用一个位表达，不隐式放大：`EDIT` 不含 `CREATE`，`DELETE` 不含 `PURGE`，`MANAGE` 不含业务操作。
- 隐藏类操作（下载、打印、分享）一律单独成位，避免「能看 = 能拿走」。

## 4. 主体与拒绝语义

主体：

| 类型 | 匹配规则 |
| --- | --- |
| `EVERYONE` | 所有**已通过库准入**的用户（公开库的任何登录用户，或私有库成员） |
| `USER` | 指定用户 |
| `DEPT` | 指定部门**及其全部下级部门** |
| `ROLE` | 用户拥有的任一系统角色 |

- 同一节点、同一主体只允许一条授权记录，记录同时保存 `allow_bits` 与 `deny_bits`。
- 命中任意条授权即累加：`allow |= allow_bits`、`deny |= deny_bits`。
- **拒绝优先**：`effective = allow & ~deny`，对祖先与自身统一生效。
- 拒绝 VIEW 等价于「对该用户隐藏该节点及其继承子树」。
- 管理员（库创建人、库管理员、超级管理员）固定拥有 `ALL`，**拒绝位对管理员无效**；
  但仍需通过「资源存在、未在回收站、属于该库」等业务校验。

库准入与内容授权分离：

- 库的公开/私有、成员关系决定「能否进入知识库」；
- 进入后默认只拿到**根节点的 VIEW**，其余能力必须显式授予；
- 私有库的 EVERYONE 授权不会自动让非成员可读（准入优先）；
- 内容授权不能突破私有库准入门槛。

## 5. 有效位计算（作用域模型）

```
resolve(node, user):
    if user 不可读 node.library:            return 0
    if user 是该库管理员:                    return ALL
    entry = 库公开 or 用户/部门已加入
    allow = deny = 0
    for n in path(root → node):             # 由物化路径直接得到
        if n.inherit_parent == false:       # 独占范围：允许与拒绝一起清空，本级重新开始
            allow = deny = 0
        if n is LIBRARY and entry:          allow |= VIEW
        for g in n.grants where g 命中 user:
            allow |= g.allow_bits
            deny  |= g.deny_bits
    # 注意：不再因为祖先不可见而返回 0
    return allow & ~deny
```

作用域语义：

- 目录/库是**授权范围**，其授权天然覆盖子树；没有单独的「继承开关」，只有「叠加 / 独占」两种范围模式。
- **对象例外**：文档自己的直接授权可以让自己可见，不要求祖先对用户可见；祖先没有授权只代表「该范围没给权限」，不代表「子对象一律不可见」。
- **DENY 仍然是全链路累加**：在祖先上 `DENY VIEW` 会隐藏整棵子树，子对象无法用 ALLOW 覆盖；要放开只能把子范围设为「独占」。
- 目录树按「容器可见性」展示：容器不可见时，子对象不在树中出现，但仍可通过搜索、收藏、最近访问直达。
- 拒绝优先；管理员固定 `ALL`。

实现要点：

- 批量鉴权（目录树、搜索、收藏、最近访问）**一次请求只查一次节点、一次授权**：
  先批量取目标节点，再由 `path` 批量补齐祖先，再一次性取回所有相关节点的授权；
  计算过程按请求缓存中间结果。
- 不缓存跨请求结果；权限变更立即生效。
- `effectiveBitsMap` 的返回值对「节点不存在」统一为 0，避免列表接口因为单条脏数据整体 500。
- 编辑器在「叠加」模式下展示上级已生效的授权；切到「独占」时把这些授权复制为本级直接授权，避免权限突变（库成员的默认查看不会被复制，需要显式添加「库内所有可访问者-查看」）。

## 6. 表结构

### 6.1 `pms_knowledge_acl_node`

| 列 | 说明 |
| --- | --- |
| `id` | 主键（雪花，应用侧生成） |
| `tenant_id` | 租户 |
| `library_id` | 所属知识库 |
| `object_type` / `object_id` | `LIBRARY` / `FOLDER` / `DOCUMENT` + 对象编号 |
| `parent_id` | 父节点，根为 NULL |
| `inherit_parent` | 是否继承父节点，根固定 false |
| `path` / `depth` | 物化路径与深度 |
| `version` | 权限版本号，保存时做乐观锁 |
| 审计列 + `deleted` | 沿用项目基类；唯一索引带 `WHERE deleted = 0` |

索引：`(tenant_id, object_type, object_id) WHERE deleted=0` 唯一、`(parent_id)`、`(tenant_id, library_id)`。

### 6.2 `pms_knowledge_acl_grant`

| 列 | 说明 |
| --- | --- |
| `acl_node_id` | 节点 |
| `principal_type` / `principal_id` | `EVERYONE`（id 为空）/ `USER` / `DEPT` / `ROLE` |
| `allow_bits` / `deny_bits` | 允许位、拒绝位（0~8191） |

约束：`allow_bits <> 0 OR deny_bits <> 0`；`allow_bits = 0 OR (allow_bits & 1) = 1`；
同节点同主体唯一（`EVERYONE` 单独部分唯一索引）。

### 6.3 `pms_knowledge_acl_audit`

记录 `action`（CREATE_NODE / UPDATE_GRANTS / MOVE_SUBTREE / DELETE_NODE）、操作人、
`before_snapshot` / `after_snapshot`（授权差异 JSON）、所属库与节点。只用于追溯，不参与鉴权。

## 7. 对象生命周期

| 动作 | 服务端校验 | ACL 处理 |
| --- | --- | --- |
| 建库 | 系统权限 + 创建人 | 同一事务内建根节点 |
| 建文件夹/文档 | 父节点 `CREATE` + 库可读 | 同一事务建子节点，默认继承 |
| 改属性/正文/新版本 | 当前对象 `EDIT` | 不变 |
| 删除（进回收站） | 当前对象 `DELETE` | **保留**节点与授权（回收站仍可展示原路径） |
| 恢复 | 原对象 `EDIT` + 目标父节点 `CREATE` | 父节点仍被删除时重挂到库根并重写 `path` |
| 同库移动 | 源 `MOVE` + 目标父 `CREATE` | 重写子树 `path`，保留授权 |
| 跨库移动 | 源 `MANAGE` + 目标父 `CREATE` + **显式确认重置权限** | 删除子树直接授权、全部回到继承、重写 `path` 与 `library_id`，写审计 |
| 彻底删除 | 回收站 `PURGE`/库管理员 | 同一事务清理节点与授权并写审计 |
| 复制（内容包导入等） | 来源 `VIEW`/`EXPORT` + 目标父 `CREATE` | 新建独立节点，继承目标，不复制旧库授权 |
| 分享 | 当前对象 `SHARE` 或 `MANAGE` | 分享令牌独立，对象删除/撤销后立即失效 |

跨库移动显式重置是刻意的：它避免「把一个受限子目录移动到目标库后，被目标库更宽的授权意外放开」，
也避免把源库的成员名单带到目标库。前端必须二次确认并展示「将清除 N 条直接授权」。

作用域模型下，移动会改变对象落入的授权范围：同库移动到「独占」目录会按目标目录的授权重新计算，
即使保留直接授权也可能失去/获得访问。这是作用域语义而不是缺陷；前端应在移动前提示目标范围的访问模式，
后续可增加「移动影响预览」（列出将失去/获得的授权），本次未实现。

## 8. 统一鉴权入口

权限判断只有两层，禁止在 Mapper、前端、SQL 里二次判断权限：

- `PmsKnowledgeAclService`：唯一计算与写入入口，负责节点、路径、允许/拒绝位、版本、审计；
- `PmsKnowledgeContentPermissionService`：业务侧统一门面，负责「按对象 permission_id 找到节点 → 校验操作位」，
  并按能力细分为 readable / writable / deletable / manageable / sharable / movable / purgeable /
  reviewable / exportable / interactable，业务服务只允许调用这一层。

所有列表接口（目录树、搜索、标签、收藏、最近访问、互动、回收站）必须先用 `effectiveBitsMap`
批量算位再过滤，不允许「先返回再隐藏」。业务状态规则（草稿仅创建人可见、回收站不可直达）由对应服务在调用门面前后统一校验。

## 9. API 与前端

- `GET /pms/kb/acl/get?id=` 或 `?objectType=&objectId=`：返回节点、`version`、`inheritParent`、有效位、
  我的授权来源 `sources`、上级已生效授权 `inheritedGrants`；拥有 `MANAGE` 时额外返回完整 `grants`，否则为 `null`（不泄露成员名单）。
- `PUT /pms/kb/acl/update`：提交 `objectType/objectId/inheritParent/expectedVersion/grants[]`，
  每条授权带 `allowBits`、`denyBits`；版本不一致返回「权限已被其他人修改」。
- `GET /pms/kb/acl/audit-list`：`MANAGE` 或库管理员可查最近变更。
- 前端权限编辑器：访问范围开关（叠加/独占）、继承自上级的只读授权、授权表（主体 + 允许位 + 拒绝位 + 全选）、
  切换独占时的提示与自动复制、保存冲突提示；资源详情/目录树/搜索统一返回 `effectivePermissionBits`，
  按钮按位渲染；旧的 `currentUserLevel` 仅作过渡，不再参与任何判断。

## 10. 并发、审计与日志

- 保存 ACL：先 `SELECT ... FOR UPDATE` 锁节点，再校验 `expectedVersion`，
  条件更新 `version = version + 1`；纯差量写 grant。旧页面保存必然冲突而不是覆盖。
- 移动/恢复：同一事务内更新子树 `path` 与节点版本，失败回滚。
- 每次保存/移动/建节点/删节点写审计快照（授权差异、路径变化、操作人）。
- 鉴权失败日志只记录 `nodeId/objectId + action + userId`，不记录标题、文件名、分享令牌。
- `MANAGE` 不允许通过保存把最后一个管理者移除（切为独占且无 MANAGE 允许位时拒绝，库管理员除外）。

## 11. 迁移与部署

**存量数据必须迁移**（标准安装脚本 `pms-2026-09-03-data-pg.sql` 自带知识库种子数据）：

1. `pms-knowledge-acl.sql`：**必须在与 PMS 业务表相同的 schema 下执行**（例如 `SET search_path TO mes, public;`），
   否则会因找不到 `pms_knowledge_document` 中止；脚本已内置前置校验，错误 schema/库上不会创建任何 ACL 表。
   建表（新库）或加列（v1 已执行过的库），
   然后按库 → 文件夹（自顶向下）→ 文档（父文档/文件夹/库根）回填节点；
   把旧 `permission_id` 指向的旧权限（`open_status/open_level`、协作者 `level`）映射为 allow 位；
   最后回写 `folder/document.permission_id = ACL 节点 id`。
2. 执行文末自检 SQL：缺少节点、`permission_id` 未回写、断链、跨库节点**必须全部为 0**。
3. 发布应用（前后端同版）。**不得**只发布一端或只执行一半 DDL。
4. 验收通过后执行 `pms-knowledge-acl-drop-legacy.sql`：它先把旧表改名为 `*_bak_时间戳` 保留，
   确认无误后再手工删除。应用回滚时可用备份表恢复旧数据。
5. 回滚：应用回滚 + 从备份恢复旧表；新表保留不影响旧版本运行。

旧等级 → 新操作位映射：

| 旧等级 | 新允许位 |
| --- | --- |
| 1 管理 | `ALL`（8191） |
| 2 编辑 | VIEW/DOWNLOAD/CREATE/EDIT/DELETE/MOVE/REVIEW/INTERACT（2655） |
| 3 预览 | VIEW（1） |
| 4 下载 | VIEW/DOWNLOAD（3） |
| 5 上传下载 | VIEW/DOWNLOAD/CREATE（7） |

映射是「能力不缩小」的原则：旧「编辑」在首版实现里其实已包含删除，因此保留 DELETE 并补上 MOVE/REVIEW/INTERACT。

## 12. 性能预算

- 单资源鉴权：≤ 3 次查询（节点 + 祖先 + 授权），且同一请求内复用。
- 列表/树/搜索：每页 ≤ 1 次节点查询 + 1 次授权查询，**不得随结果条数线性增长**。
- 同一 HTTP 请求内对已算过的节点做请求级缓存（key = userId + nodeId），授权写操作后立即失效，
  因此目录树这类「同一批节点被多处计算」的接口不会重复打库。
- 目标：1 万文档的库，目录树接口 ACL 相关查询 ≤ 4 条，P95 增量 < 50ms。

## 13. 验收矩阵

| # | 场景 | 预期 |
| --- | --- | --- |
| 1 | 公开库，只有根默认 VIEW | 可进入、可看，不能新增/编辑/删除/下载 |
| 2 | 私有库非成员 | 列表、搜索、直达、预览、下载全部拒绝 |
| 3 | 上级部门获 VIEW+EDIT，个人另获 DOWNLOAD | 下级部门用户得到三个位并集 |
| 4 | 父目录 EVERYONE 可读，子目录关继承并只授某人 | 其他人看不到子目录及其搜索结果 |
| 5 | 父目录可读，子目录对某部门 DENY VIEW | 该部门看不到子目录，其他部门正常 |
| 6 | 父目录不可见，文档有直接授权 | 文档可直达（不出现在目录树），祖先 `DENY VIEW` 时仍不可见 |
| 7 | 只有 VIEW 无 DOWNLOAD | 可预览，下载端点拒绝 |
| 8 | 有 CREATE 无当前对象 EDIT | 可在目录新增，不能改目录自身 |
| 9 | 有 EDIT 无 CREATE | 可改名/改内容，不能新增子项 |
| 10 | 有 SHARE 无 MANAGE | 可管理分享，不能改 ACL |
| 11 | 撤销授权 / 退出部门 / 角色被移除 | 下一次请求立即拒绝，刷新后按钮消失 |
| 12 | 两个管理员同时保存同一节点 | 后保存者收到版本冲突，不覆盖前者 |
| 13 | 切换为独占并清空授权 | 拒绝保存（最后一个管理者保护），库管理员可强制；切换时自动复制上级授权 |
| 14 | 同库移动 / 跨库移动 | 前者保留授权，后者需显式确认并清空直接授权、写审计 |
| 15 | 恢复回收站对象 | 校验 EDIT + 目标父 CREATE；父已删则挂根并重写 path |
| 16 | 历史版本、审阅、分享、收藏、最近访问 | 与当前对象可见性一致；撤权后不再泄露标题/地址 |
| 17 | 权限变更后审计 | 能查到操作人、时间、变更前后授权 |

证据要求：数据库迁移自检 SQL、ACL 单元测试、服务端编译、前端类型检查、
浏览器双账号回归（含一次并发保存与一次跨库移动）。

## 14. 附录 A：相对首版的变更

| 首版 | v2 | 原因 |
| --- | --- | --- |
| 6 个操作位 | 13 个操作位 | 移动/分享/彻底删除/审阅/导出/互动/打印无法用旧位表达 |
| 祖先不可见即整棵子树不可达 | 对象直接授权可生效；祖先 `DENY VIEW` 仍全链路生效 |
| 只有允许 | 允许 + 拒绝，拒绝优先 | 不关闭继承就能收窄子目录，避免「一刀切断链」 |
| 主体只有全员/用户/部门 | 增加角色 | 与系统角色体系对齐 |
| 逐级递归查父节点 | 物化路径 + 批量查询 | 首版每个节点都要走一遍祖先链，列表接口 N+1 |
| 无并发控制 | `version` + 行锁 + 冲突提示 | 旧页面保存会静默覆盖新授权 |
| 无审计 | 审计表 + 差异快照 | 权限变更不可追溯 |
| 假设空库、直接 DROP 旧表 | 幂等迁移 + 自检 + 备份表 + 延后删除 | 标准安装脚本自带知识库数据，直接 DROP 会串权限 |
| 跨库移动静默清空授权并全部改继承 | 需显式确认 + 审计 | 静默改动会放大或收窄权限 |
| 预览票据复用 OnlyOffice JWT 密钥 | 独立 `pms.kb.preview-secret`，票据绑定文档+版本+用途 | 文档服务器持有该密钥即可伪造票据越权读数 |
| 仅 `MANAGE` 可看 ACL 详情，VIEW 用户无来源 | 普通用户可看「我的来源」 | 排障需要知道权限从哪来，同时不泄露成员名单 |
